# FEX 2610 / Snapdragon 865 / FF7 Remake: ARMv8.2-A validation

Status: **experimental; no device performance result is claimed**.

## What changed, and what did not

The existing `FEXCore-2610-GameNative-O3-Snapdragon865.wcp` is the unchanged
ARMv8-A+CRC / Cortex-A77-scheduled control from
[`fexcore-2610-gamenative-soc-14c9268-pre.1`](https://github.com/Ragnarok93/FEX/releases/tag/fexcore-2610-gamenative-soc-14c9268-pre.1).

The new `FEXCore-2610-GameNative-O3-Snapdragon865-v82.wcp` is an *additional*
candidate compiled from the **same exact FEX-2610 source commit**
`14c92681f4d62cf84d901460e0358de09c8847a7`.
It changes only the native C/C++ ARM ISA target from `armv8-a+crc` to
`armv8.2-a+crc`; `-mtune=cortex-a77`, `-O3`, disabled LTO and the
toolchain stay the same. FEX's own ARM JIT code-generation paths are unchanged.

The build passes `-DTUNE_ARCH=armv8.2-a` to the FEX CMake project; FEX
automatically appends `+crc`. It **does not** place only `-march` in
`CMAKE_CXX_FLAGS_RELEASE`, which can be overridden by later project
flags. A Python verifier checks the *last effective* `-march`, `-mtune`,
and compiler architecture in at least 10 FEX/Windows translation units
for **both ARM64EC and aarch64** build outputs, failing closed on mismatch.

ARMv8.2-A is supported by the Snapdragon 865's Cortex-A77- and Cortex-A55-
derived CPUs, but this assumption must still be verified by real on-device
execution and correctness tests. Do not force SVE, higher ISA levels,
unchecked extensions, or incorrect Wine processor registry values.

- Build entry point: `Scripts/GameNative/build_fexcore_2610_wcp.sh`
- Variant: `o3-snapdragon865-v82`

- Release artifact: **only the newly named WCP plus checksum**, containing
  `profile.json`, `system32/libarm64ecfex.dll`, and
  `system32/libwow64fex.dll`
- The established SoC prerelease, its branch, and its WCPs remain unchanged.
- Smoke/contract: `bash .github/scripts/test-build-fexcore-2610-wcp.sh`,
  `bash .github/scripts/test-package-fexcore-2610-wcp.sh`,
  `python3 -m unittest discover -s .github/scripts -p test_fex2610_tools.py -v`

## FF7 Remake S20+ test protocol

1. Install both versions as independent content profiles into **the same**
   GameNative build. Preserve a backup of the working container and save.
   Use Bionic Proton 10 ARM64EC, the FEX emulator and the same Wine prefix.
2. Keep the same Mr. Purple T30 Turnip driver, VKD3D version, game save,
   1152x648 resolution and graphics settings. Disable LSFG / native frame
   generation. Disable external FPS interpolators and use genuine displayed
   frames. If the GPU is saturated, expect little or no FPS change.
3. Use the same container environment for both candidates:
   `FEX_DISKCACHE=1`, `FEX_DISKCACHEMEMORYSIZE=33554432`;
   retain the same TSO, multiblock, x87, and L1/L2 preset settings.
   `FEX_PROFILESTATS=1` is optional for separately supported FEX
   profiling integrations; it does not substitute for displayed-frame
   measurements, and GameNative is not guaranteed to export those stats.
4. Select control, cold-launch FF7 Remake, verify menu, loading,
   cutscene, combat, fast camera turns, and 15+ minutes of traversal.
   Record correctness issues, crashes, thermal/frequency telemetry
   if available, and *actual game/display presentation timestamps*.
   Repeat with warmed cache, then run the candidate identically.
5. For statistical comparisons take at least three warmed passes of the
   same 2-5 minute scene per candidate. Alternate the order of
   candidates to reduce thermally biased results. Keep each raw CSV,
   selected WCP name/SHA256, settings, date, observed thermal state,
   GPU driver, and GameNative commit.
6. Obtain real per-game presentation intervals from your graphics
   profiler or frame trace, **not** inferred from the app UI frame
   counter, an LSFG synthetic cadence, or arbitrary GameNative log
   timestamps. Export either a CSV header `frame_time_ms` with one
   *positive real frame interval* per line, or a CSV header
   `present_time_ns` with strictly increasing timestamps. Do not treat
   the timestamps of queued/generated frames as actual display presents.
7. Compare one control/candidate pair:

   ```bash
   python3 Scripts/GameNative/benchmark_fex2610_frametimes.py \
     --baseline control-warm.csv --candidate v82-warm.csv \
     --warmup-seconds 15 --json-out ff7r-v82-comparison.json
   ```

The analyzer reports mean FPS, 1% low derived from the slowest 1% frame
durations, p95/p99 frame durations, standard deviation, and >50 ms events.
It rejects invalid, empty, non-monotonic, or insufficient samples.
**These frame times are not automatically attributable to FEX**.

## Promotion criteria

Treat the new candidate as experimental until all of these hold:

- WCP checks and effective compile-command attestation pass in CI.
- Both DLLs load with the expected ARM64EC/WoW64 paths on the S20+.
- No regression in loading, saves, combat, stability or visuals.
- No unacceptable thermal or peak-memory regression.
- Repeated, same-scene warm-cache measurements show a consistent
  improvement in p99/p95 frame time, 1% low, or throughput beyond
  measurement noise. If inconclusive, retain the existing control.

## Next research gates (not implemented in this candidate)

- Confirm `tu_override_uncached_as_cache_coherent` reaches Turnip.
- Measure native FEX host feature detection (including atomics) under Wine.
- Separately measure warmed disk-cache hits, L1/L2 lookups, and JIT stalls
  before changing code generation.
- Defer JIT memory-order relaxations, LTO and PGO until explicit,
  correctness-preserving validation is available.
